## 5. THE HARD PARTS — WHAT'S ACTUALLY BEING GRADED

1. **Grounding** — prices, GST, stock always come from the DB via tools. The LLM never invents a business fact.
2. **Oversell guard** — stock can never go negative. Enforced at the tool/DB layer, never hoped for via prompt wording.
3. **GST correctness** — per-item slab (0% / 5% / 12% / 18%), CGST+SGST split, correct rounding, legible tax breakup on the bill.
4. **Multi-turn bills** — bill builds as a draft over several messages, supports edits, only decrements stock on finalize.
5. **Idempotency** — Telegram redelivers messages. A retried "finalize" must not double-bill or double-decrement stock.
6. **Concurrency** — two bills (or a bill + a stock-in) happening near-simultaneously must not corrupt stock.
7. **Guardrails** — don't sell below cost, don't delete stock, don't settle a khata that doesn't exist — confirm or refuse.
8. **Real artifacts** — actual GST-correct PDF invoice and a PPTX deck with real charts, generated by tools, not screenshots or plain text.
9. **Memory across sessions** — preferences persist in the database, not the conversation window.

## 6. THE SINGLE MOST IMPORTANT RULE

**The LLM is NOT the source of truth.**

It never invents inventory quantities, prices, GST rates, customer balances, sales totals, payment records, or invoice values. All of these come from tools hitting the database. The LLM's job is to understand language, decide which tool(s) to call, and explain results in natural language — nothing more.

## 12. PROPOSED SCHEMA — REVIEW, DON'T BLINDLY ACCEPT

This is a working draft. Your job in this stage is to critique it against every requirement in Section 5, not just implement it as-is.

**products**
```
id, name, unit_type (packet/kg/g/litre/ml/piece/dozen),
is_loose (bool), cost_price, sell_price, gst_rate, hsn_code,
reorder_level, created_at
```

**inventory**
```
product_id (PK/FK), quantity (numeric — supports fractional kg), updated_at
```
Must enforce `quantity >= 0` at the DB/business layer — never rely on the LLM or prompt wording for this.

**inventory_transactions** (stock movement history — added so we can answer "how did stock become X")
```
id, product_id, type (receive/sale/adjustment), quantity (+/-), reference, note, created_at
```

**customers**
```
id, name, phone, created_at
```

**sales** (the multi-turn bill)
```
id, customer_id (nullable — walk-ins allowed), status (draft/finalized/cancelled),
payment_mode, payment_ref, subtotal, cgst_total, sgst_total, grand_total,
request_id (unique — idempotency key for finalize), telegram_chat_id,
created_at, finalized_at
```
`telegram_chat_id` is needed because bills are multi-turn over a chat — we need a reliable way to find "the currently open draft for this conversation."

**sale_items**
```
id, sale_id, product_id, quantity, unit_price (snapshot), gst_rate (snapshot), line_total
```
`unit_price` and `gst_rate` are snapshotted at time of adding to the bill — if a product's price changes tomorrow, past invoices must not change.

**khata_accounts**
```
customer_id (PK/FK), balance (current/cached value), updated_at
```

**khata_txns** (ledger — source of truth history)
```
id, customer_id, type (credit/payment), amount, sale_id (nullable), note, created_at
```

**preferences**
```
key (PK), value, updated_at
```

**request_log** (generic idempotency)
```
request_id (PK), response (jsonb), created_at
```

**Review this against:** overselling protection, concurrency safety, idempotency, GST correctness, draft-bill/Telegram-conversation ownership, inventory auditability, khata consistency. Propose constraints, indexes, and foreign keys as part of your review — don't just take the column lists above as final.

## 13. CRITICAL SAFEGUARDS TO KEEP IN MIND WHILE DESIGNING

- **Overselling:** reject at the tool/DB layer if requested quantity > available stock.
- **Idempotency:** a retried finalize/receive-stock/record-payment must not duplicate the effect.
- **Concurrency:** two near-simultaneous sales against the same stock must not both succeed into negative inventory — use proper transaction/locking, not naive read-then-write.
- **Transactions:** billing finalize should be atomic — check stock, create sale, create sale_items, decrement inventory, record movement, update khata if credit — all in one transaction, rollback on any failure.
- **GST:** deterministic backend calculation only — taxable amount, GST, CGST/SGST split, rounding, totals. Never LLM-calculated.
- **Guardrails:** destructive/ambiguous requests ("delete that") should not silently execute — confirm or refuse.
